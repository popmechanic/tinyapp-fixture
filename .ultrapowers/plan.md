# tinyapp-lint — three rules over seeds and expected states, run as `bun run lint:state`, zero findings on the fixture at BASE

**Grammar:** claims-v1

**Claim:** A workspace package `packages/tinyapp-lint` on the fixture (popmechanic/tinyapp-fixture), beside `tinyapp-exam`, exposing `bun run lint:state` at the root, which reads every file under `state-exams/seeds/` and `state-exams/expected/` through the app's schema and applies three rules, printing one line per finding in `@shadcn/lint`'s shape — what is wrong, in the app's vocabulary, and the fix — and exiting non-zero on any finding (quoted from #999)
**Summary:** This adds a linter for the app's saved states — the seed and expected files an exam is written against — so a state an author wrote from memory is checked before anything runs. It exists because two of the five plans on 2026-09-14 parked on exactly that: an expected file with the wrong row done, and a view no two-row state could satisfy, which the exam could only report after a launch. After this run, `bun run lint:state` says in one line per problem which row breaks which rule and what to change, in milliseconds and with no browser, so a wrong state costs a sentence at authoring instead of a parked run.

**Goal:** the first-wave ticket of map #998 (both on popmechanic/ultrapowers — `#999` and `#998` in this plan are the plugin's issues, not the fixture's, which is why there is no `**Closes:**` line). Choices made without the operator (asleep, pre-authorized), each on the quality-then-tokens-then-clock rule: (1) selector cardinality over an expected state is read from a static render of the app's own components — `react-dom/server`'s `renderToStaticMarkup` under a TinyBase `Provider` holding a store seeded with the state, with each input's `checked` attribute reflected onto `data-checked` so `tinyapp-exam`'s own `assertView` is the judge — measured at BASE: 4.3 ms for the first render, under 1 ms after, `checked=""` on the ticked box, `1 of 2 done` in the counter; a hand-written model of the markup was rejected as a second truth. (2) The reachability walk draws its arguments from the seed's cells **and the expected file's cells** plus both files' row ids and one literal per type (`'lint'`, `1`, `true`, `false`) — the issue names the seed's cells alone, under which `one-open-todo.json` is unreachable from `empty.json` (`buy milk` is in no cell of an empty seed) and every honest "add a todo" plan would draw a false finding; bounded at 3 moves and 2,000 distinct states per seed, measured worst case (an unreachable target, full exploration over the three seeds) 570 ms, the fixture's four expected files all reached at depth ≤ 1. (3) The exported callbacks are the store module's exported functions with at least one parameter whose names do not start with `create` or `read` — at BASE exactly `addTodo`, `clearCompleted`, `deleteTodo`, `setTodoCompleted`; `createTodosStore` declares one optional parameter and would otherwise be walked. (4) Exam specs are captured by importing each exam file in a child `bun` with a preloaded plugin that rewrites its `tinyapp-exam` and `bun:test` imports to stubs, never in the calling process — `Bun.plugin`'s `onResolve` did not fire on bare specifiers under Bun 1.3.0, `onLoad` on the exam files did (measured, 7 files in 6 ms), and a plugin left registered inside `bun test` would rewrite the fixture's own exams out of the suite. (5) Two waves: the four rule modules live under `packages/tinyapp-lint/`, whose dependencies exist only once the package manifest is installed, and each rule's exam runs the rule over the context the loaders build — runtime, not shape — so the rules wait one wave on the skeleton. (6) run-7's wrong-row contradiction is not a reachability finding — `two-todos-one-done.json` is one `setTodoCompleted` from `two-open-todos.json` — it is caught through its `checked` view, whose finding names `#todo-1`, the box the first click never touches. (7) The exams here are Bun tests over the linter, not state exams: the deliverable is a tool, not app behaviour. Every literal below was computed at `c2a75c6a`, none from memory.

**Spec:** popmechanic/ultrapowers#999 (the ticket) and #998 (the map, rules 1–6); `skills/ultrawrite/references/greenfield-stack.md` §State exams (the `view` vocabulary and the `[tables, values]` snapshot shape, restated in Context).

**Parallelization rationale:** wave 1 has width 1 — Task 1, the package skeleton, its loaders, the static page and the root script; wave 2 has width 4 — Tasks 2, 3, 4 and 5, one per rule, each a new file under `packages/tinyapp-lint/src/rules/` discovered by directory listing, never a line appended to a registry. The one chain, Task 1 → each of Tasks 2–5, is a runtime need and not a shape: a rule module under `packages/tinyapp-lint/` resolves `tinybase`, `node-html-parser` and `tinyapp-exam` only from the dependency tree `bun install` makes of the manifest Task 1 writes (the root `node_modules` at BASE holds `tinyapp-exam`, `typescript` and `@types` and nothing else), and each rule's exam runs the rule over the context `loadContext` builds — the captured exam specs, the schema-typed snapshots, the static render — which no contract can promise, only the installed and loaded tree.

## Global Constraints

- Check: bun run typecheck
- `bun run lint:state` on the fixture's own seeds, expected states and exams reports zero findings: a rule that fires on a file the fixture already carries is a plan defect, not a finding.
- The linter opens no browser and dials no network: a state is rendered with `react-dom/server` over the app's own components, and an exam's spec is read without running the exam.
- Every finding is exactly one line, `<file>: <subject>: <what is wrong> — <the fix>`, written in the app's vocabulary — table, row and cell ids, the invariant's own message, the exam's own selector — and every fix is concrete.
- `packages/tinyapp-exam`, the snapshots under `state-exams/` and the exams under `tests/state-exams/` are not edited by this plan.
