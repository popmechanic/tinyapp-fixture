# The filter bar — All, Open and Done above the list, the counter still counting every todo

**Grammar:** claims-v1

**Claim:** I can switch the list between all, open and done todos, and the counter still counts every todo whatever the filter shows. (elicited)
**Summary:** This adds a three-way filter above the list. It exists because a filter is the classic case where the visible list and the stored rows differ, which is exactly what a state exam plus a view assertion catches. After the run, picking Open or Done hides the other rows and the top-bar count is unchanged.

**Goal:** The fixture's store gains a values schema with one entry, `filter`, of type string and no default, and a callback `setFilter(store, filter)` that records `'all'`, `'open'` or `'done'` and ignores any other string; a pure `admits(filter, completed)` says which rows a filter shows and `filterOf(value)` reads an absent or unknown value as `'all'`; a `FilterBar` of three buttons (`#filter-all`, `#filter-open`, `#filter-done`, the active one carrying `data-active="true"`) sits above `#todoList`, the list renders only the rows the filter admits, `#doneCount` still counts every row, and the static page the linter renders agrees with the live one; every existing seed, expected state and exam is untouched, and the linter's own exams that pin the callback list and the fixture's counts are updated to the grown fixture.

**Tech Stack:** Bun + TypeScript + TinyBase (`tinybase/with-schemas` 9.7.0, a `MergeableStore` under `TABLES_SCHEMA` and, from this plan, a values schema), React (`tinybase/ui-react/with-schemas` hooks re-exported from `client/src/Store.tsx`); the `tinyapp-exam` state exams under `tests/state-exams/` with seeds and expected states under `state-exams/`; `bun run typecheck`, `bun run lint:state`, `bun test`.
**Exam command:** bun test {paths}

**Spec:** popmechanic/ultrapowers#867 (the trio of fixture plans); popmechanic/ultrapowers#998 (the map). The sitting's one design question — where the chosen filter lives — was put as "In the store's values" vs "In React state" and the operator picked the store's values. The values entry carries no `default`: measured at BASE, a values schema with `default: 'all'` makes `getContent()` spell `{filter: 'all'}` on every store, which turns all seven existing snapshot files, seven of the fixture's exams and three of `packages/tinyapp-exam`'s own tests red (13 pins beyond the snapshots), where a schema without a default leaves every one of them byte-for-byte as it was; an absent value reads as `'all'` in the page.

**Parallelization rationale:** three waves — wave 1 is two wide (Task 1, the store; Task 2, the pure predicate), wave 2 is Task 3 alone, wave 3 is Task 4 alone. Task 3 waits on both wave-1 tasks for runtime behaviour, not shape: its exam opens the page over a seed, clicks `#filter-open` and expects a state whose values half only the real `setFilter` writes and whose reachability the linter establishes by walking that very callback, and the one row it expects to see is whichever `admits` admits — a bar over a store that cannot hold the value, or a list over a predicate that admits everything, passes neither the store move nor the view. Task 4 waits on Task 3 for runtime behaviour too: its exam clicks `#filter-done`, a button only Task 3's bar renders, and a second page bundle cannot share Task 3's exam process (the `Bundle failed` trap the Global Constraints name), so the Done press is its own exam in its own task, beside the one piece of the bar Task 3 leaves undone — its stylesheet. Task 1 and Task 2 share nothing but the three filter names, which each carries as a literal in its Context. Two concurrent sibling runs on the same base add a `due` cell to `todos` and a `trash` table; this plan pins neither the table list nor the cell set of a row.
