# The two interaction exams — the checkbox completes the todo, Enter submits the input, every literal computed at BASE

**Grammar:** claims-v1

**Claim:** When I read a task's evidence, I can see that a real click in a real browser reached the state the task claimed, with the screenshot beside it, and that the exam would have gone red if it hadn't. (elicited)
**Summary:** This lands the two exams run-7 ran green but could not produce, because their plan pinned a state the click never reaches. It exists so the fixture carries, on its main branch, one exam that clicks a checkbox and one that types and presses Enter, each proving what the interaction did to the app's state with the screenshot beside it. After this run a task on a TinyApp can be judged on a real interaction in a real browser, and a reader of its evidence can see the state, the picture, and that a wrong state would have failed it.

**Goal:** the one task run-7 (fixture, 2026-09-15, `tinyapp-fixture#8` merged by hand as `c952dadd` with tasks 1–2) left unproduced, re-authored with every literal measured on `c952dadd`: the click on the first checkbox completes row `0`, so the expected state is a new file with row `0` done; the `checked` view is on `.todoItem.completed input[type=checkbox]`, the one selector whose every match is checked; the Enter exam's row is `0`, which is what `one-open-todo.json` already holds, so no second expected file. #834's decisions stand (the click and the render in the sandbox's own Chromium).

**Tech Stack:** Bun 1.x + TypeScript (`packages/tinyapp-exam`, the workspace helper; `client/`, the fixture TinyApp; `tests/state-exams/`, its exams). Test command: `bun test` from the repo root; `bun run typecheck` is the type gate.
**Exam command:** bun test {paths}

**Spec:** run-7's receipt (`ultra/evidence/run-7` on the fixture: `status.json` task 3's attention line, `state-exams/task-3/`), #834's 2026-09-15 comments, the state-exams spec `2026-09-09-tinyapp-state-exams` (§3.2, §3.4 restated in Context).

**Parallelization rationale:** one wave, width 1: a single task, because the two exams, their expected file and the README sentence are one surface with one exam over them, and splitting them would only add a second child-process exam of the same shape.

## Global Constraints

- The exam never dials a network: the page is opened from a `data:` URL, every request the page makes is blocked in the browser before it leaves, and the helper's own connection is a loopback WebSocket to a process it spawned.
- Check: bun run typecheck
- A missing browser binary is a red exam that names the path, never a skip.
- The evidence keys the engine already reads keep their names: `store-diff.json`, `dom.html`, `screenshot.png`, `mutant.json`, `contract.json`, `walls.json`.
- `packages/tinyapp-exam` is not edited by this plan; the exams are written against the helper as it is at BASE.

**Context:** The two exams are written in the shape of `tests/state-exams/buy-milk.test.ts` at BASE (`c952dadd`): `import {stateExam} from 'tinyapp-exam'`, `import {createTodosStore} from '../../client/src/storeData'`, then `stateExam({clock: '2026-01-01T00:00:00Z', entry: 'client/index.html', seed, store: () => createTodosStore(), action, expected, view, mutant})` — with `action` an `Action` object (`{click: selector}`, `{type: [selector, text]}`, `{key: [selector, key]}`) or a list of them performed in order, the forms `packages/tinyapp-exam/src/types.ts` exports at BASE. Every literal below was measured on `c952dadd` with the helper against a real Chromium, and the run-7 park was exactly a literal that was not: `client/src/TodoList.tsx` renders rows through `useSortedRowIds('todos')`, ascending by row id, so the seed `two-open-todos.json` (`{0: "buy milk" open, 1: "walk the dog" open}`) renders `#todo-0` first; `Page.act` clicks the first match of its selector, so `.todoItem input[type=checkbox]` completes row `0` — hence the new expected file `two-todos-first-done.json` (row `0` done, row `1` open; the BASE file `two-todos-one-done.json` has row `1` done and is the wrong state for this click, which is what parked run-7). `client/src/TodoItem.tsx` renders `<div className="todoItem completed">` for a done row, so `.todoItem.completed input[type=checkbox]` matches exactly the one clicked box and `checked: true` holds (the helper's `allRead` requires *every* match to read `data-checked="true"`, which the bare `.todoItem input[type=checkbox]` can never satisfy over two boxes); the measured evidence for this spec was `store-diff.json` `[]`, `mutant.json` `killed: true, path: todos/0/completed`, `dom.html` with `class="todoItem completed"` and `data-checked="true"` on `#todo-0`, `walls.json` `action_ms` 56, `browser: "ran"`. For the Enter exam, `client/src/TodoInput.tsx` renders the input with `placeholder="What needs to be done?"` and submits on Enter through `addTodo`, and `addTodo` on a store seeded from `empty.json` assigns row id `0` (`store.addRow` on an empty table; measured: `{"id":"0"}`), so the reached state is byte-for-byte `state-exams/expected/one-open-todo.json` as it exists at BASE — reuse it, create no second expected file; measured evidence: `store-diff.json` `[]`, `mutant.json` `killed: true, path: todos/0/text`, one `.todoItem` whose label is `buy milk`. The evidence directory rule is the helper's `evidenceDir` in `packages/tinyapp-exam/src/evidence.ts`: `<ULTRA_RUN_DIR>/state-exams/task-<ULTRA_TASK|none>/<stem>-<ULTRA_EXAM_PASS|none>`, `stem` the exam file's basename without `.test.ts`. A red exam still writes its record; on a wrong `expected` the outcome's `failure` is `store move: expected state not reached` followed by the diff (`packages/tinyapp-exam/src/state-exam.ts` ~174), and the `stateExam` wrapper throws it, so the child `bun test` exits non-zero with that line on its output. The exam for this task, `interaction-evidence.test.ts`, never imports the two exam files: it runs each as its own child `bun test <file>` process (`Bun.spawn` or `Bun.spawnSync`, `cwd` the repo root, `env` the process's own plus `ULTRA_RUN_DIR` pointed at a fresh `mkdtemp` directory and with `ULTRA_TASK` and `ULTRA_EXAM_PASS` unset so the path reads `task-none/<stem>-none`) and reads the evidence back. One child per exam file: on a laptop a single `bun test` process that bundles the entry twice fails the second exam with `Bundle failed` (measured at BASE with two BASE exams, `bun test tests/state-exams/buy-milk.test.ts tests/state-exams/clear-completed.test.ts`; the sandbox does not show it — run-7's task 3 ran both exams in one invocation green), so the evidence exam spawns one process per exam and the two `Run:` lines below name one exam file each. For M4 the exam writes a temporary sibling `tests/state-exams/tmp-red-<pid>.test.ts` — the click exam's text with `two-todos-first-done.json` replaced by `still-empty.json` — runs it as a child the same way, asserts the non-zero exit and the `store move: expected state not reached` line, and removes the file in a `finally`; a unique name per process keeps two concurrent runs apart, and `bun test` collects its file list at start, so a file created mid-run is never collected by the suite that spawned it. The README section is new (BASE `README.md` has no `##` heading), goes at the end, and says in plain words: an exam's action may be a `click`, a `type`, or a `key` press; the click runs in the sandbox's own Chromium (`/headless-shell/headless-shell` on the fleet image, or the binary `TINYAPP_BROWSER` names on a laptop); the evidence beside the task is the store diff, the DOM and the screenshot. The Chromium the fleet runs is on the image; on this Mac `TINYAPP_BROWSER=/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` was the binary every literal above was measured with.
